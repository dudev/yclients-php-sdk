# Задачи SDK — верхнеуровнево

Статус: инфраструктура репозитория готова, кода клиента ещё нет. Ниже — что должен уметь SDK,
собрано из двух реальных потребителей в проекте relsy: `relsy-yclients-records` (сущность
`Appointment`) и `relsy-yclients-clients` (сущность `Client`) — оба сейчас на стадии теханализа,
см. `docs/yclients-records-design.md` и `docs/yclients-clients-design.md` в `relsy/backend` (и в
соответствующих `relsy-yclients-*` worktree). Всё, что ниже помечено как подтверждённое —
подтверждено вручную через `developers.yclients.com` (SPA, не отдаётся автоматическому fetch, нужен
реальный браузер) и реальными вебхуками из продакшен-данных, не из документации вслепую.

Это **SDK, не тонкий клиент** — то есть, помимо самих HTTP-вызовов, ожидаются: типизированные
DTO ответов, обработка пагинации, управление токенами (получение/обновление `user_token`),
единообразная обработка ошибок API, а не только голые методы `getX()`/`postX()`.

## 1. Базовые протокольные вещи (общие для всех методов)

- База: `https://api.yclients.ru`.
- Версия ответа — заголовок `Accept: application/vnd.yclients.v2+json`, обязателен на каждый запрос.
- Конверт ответа: `{ "success": bool, "data": ..., "meta": ... }` — SDK должен разворачивать его сам,
  потребитель получает либо типизированный результат, либо исключение, не сырой конверт.
- Авторизация: `Authorization: Bearer <partner_token>` или `Bearer <partner_token>, User <user_token>`
  — часть методов требует только partner-токен, часть — оба (см. §3, где именно). `partner_token`
  относительно статичен (выдан один раз при регистрации приложения в Marketplace), `user_token`
  получается через `POST /api/v1/auth` (логин/пароль, опционально 2FA) и годен, пока не сменится
  пароль пользователя — SDK должен предоставить и получение, и (по необходимости) обновление, не
  просто «передайте токен строкой», раз токен — часть протокола, а не только конфигурация.
- Лимит: 200 запросов/мин или 5/сек на IP — SDK может как минимум явно поднимать типизированное
  исключение при HTTP 429 (если YClients так отвечает при превышении — не проверено на реальном
  трафике, уточнить при реализации), необязательно строить полноценный rate-limiter внутри с первой
  версии.
- Формат дат — ISO 8601 (`"2014-09-21T23:00:00.000+03:00"`); длительности — в секундах, не в
  минутах/часах.

## 2. Компании (`Branch` ↔ `company_id` в relsy)

- `GET /api/v1/companies` — список, фильтры `id`, `group_id`, `active`, `moderated`. **Только
  `partner_token`**, `user_token` не нужен.
- `GET /api/v1/company/{id}/` — детали одной компании (адрес, телефоны, соцсети, координаты).
  Требует `user_token`.
- `GET /api/v1/group/{group_id}/clients/?phone=...` — поиск клиента по телефону во всей сети
  салонов. Подтверждено, что нужен (в relsy два известных `company_id` состоят в одной сети), но
  сама сеть в текущем дизайне relsy не используется для склейки клиентов (см.
  `yclients-clients-design.md`) — метод стоит реализовать для полноты покрытия API, не как то, от
  чего сейчас что-то в relsy зависит.

## 3. Сотрудники (`Employee` ↔ `staff_id` в relsy, справочно)

- `GET /api/v1/staff/{company_id}[/{staff_id}]` — список/один сотрудник. **Только `partner_token`**.

## 4. Записи (`Appointment` в relsy)

- `GET /api/v1/records/{company_id}` — список, `partner_token`+`user_token`. Параметры:
  `page`/`count`, `staff_id`/`client_id`/`created_user_id`, `start_date`/`end_date` (дата сеанса),
  `c_start_date`/`c_end_date` (дата создания), **`changed_after`/`changed_before`** (инкрементальная
  синхронизация), **`with_deleted=1`** (включить удалённые явным флагом).
- `GET /api/v1/record/{company_id}/{record_id}` — одна запись, та же авторизация.
- `attendance` в ответе — код `2`/`1`/`0`/`-1` (подтвердил / пришёл / ожидание / не пришёл) —
  задокументировано официально, SDK может отдавать как enum, не сырое число, раз смысл уже известен.

## 5. Клиенты (`Client` в relsy)

- `GET /api/v1/clients/{company_id}` — список, `partner_token`+`user_token`. Фильтры: `fullname`,
  `phone`, `email`, `card`, `paid_min`/`paid_max`, `id`/`id[]`, `changed_after`/`changed_before`.
  У этого метода **нет** `with_deleted`-аналога (в отличие от записей) — не подтверждено, шлёт ли
  YClients вообще сигнал об удалении клиента.
- `GET/PUT/DELETE /api/v1/client/{company_id}/{id}` — одна карточка. `POST` (создание, в т.ч.
  массовое через `/bulk`) — relsy не создаёт клиентов в YClients, но метод стоит реализовать для
  полноты SDK (сторонние потребители пакета могут захотеть).
- Мелкая неровность в самом YClients: тело создания называет теги клиента `categories`, тело
  редактирования — `labels`, для одного и того же поля.

## 6. Вебхуки — вне рамок SDK (пока)

Приём вебхуков в relsy идёт через отдельную Cloud Function (не PHP) и, возможно, HTTP-вызов оттуда
в `relsy-backend`, а не через прямую подписку SDK на вебхуки YClients — см. `yclients-records-design.md`
§5. SDK может позже получить хелперы для разбора тела вебхука (та же форма `{company_id, resource,
resource_id, status, data}`, что и у REST-ответов на `record`/`client`/`staff`/...), но это не
блокирует первую версию и не входит в неё по умолчанию.

## 7. Явно не входит в SDK

- Матчинг `company_id`/`staff_id`/`client_id` на сущности relsy (`Branch`/`Employee`/`Client`) —
  это бизнес-логика потребителя (`relsy-backend`), не протокольная часть YClients API.
- Хранение/синхронизация данных (`YclientsClientSyncService`/`AppointmentSyncService` и т.п.) —
  тоже в `relsy-backend`, SDK только предоставляет типизированный доступ к самому API.
